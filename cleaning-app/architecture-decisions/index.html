    掃除アプリ アーキテクチャ決定ログ

    掃除管理アプリで下したアーキテクチャ上の意思決定と、その背景・トレードオフを記録する。

    サーバーファースト vs ローカルファースト

    決定: ユーザーデータは全てサーバー（PostgreSQL）に保存する。

    当初はデータを端末ローカルに保存する案も考えたが、最終的にサーバー保存に振った。

    • 採用理由:
      • このアプリは自宅 WiFi 環境での利用が前提なので、サーバー往復のレイテンシは許容できる。
      • ローカルファーストにすると「端末とサーバーの同期」「コンフリクト解決」のロジックが必要になり、複雑さが跳ね上がる。これを丸ごと回避できる。
      • 機種変更しても、サーバーにデータがあれば引き継ぎが自然にできる。
    • MVP の識別方式: 認証はまだ入れず、初回起動時に発行した UUID をユーザー識別子として使う。これを room.user_id に保存し、他人のデータと分離する。
    • トレードオフ: オフライン時はほぼ操作できなくなる。自宅 WiFi 前提なので MVP では許容するが、将来オフライン対応が要るならローカルキャッシュの導入を再検討する。

    なぜ Spring Boot + Kotlin を継続するか

    決定: BaaS に逃げず、自前バックエンド（Spring Boot + Kotlin）を継続する。

    • 比較対象: Supabase などの BaaS を使えば、DB・認証・API を一気に用意でき、開発は速い。
    • 採用理由: このプロジェクトは学習目的・実績作り目的を兼ねている。認証・DB 設計・レイヤー構成を自分で組むこと自体に価値があるため、あえて自前バックエンドを選ぶ。
    • トレードオフ: 自前実装は手間がかかる（認証も後で自分で組む）。その手間と引き換えに、設計・運用の経験を得る、という判断。

    MyBatis vs JPA

    決定: MyBatis を採用する。

    • 選択理由: SQL を明示的に制御したいから。JPA（Hibernate）は便利だが、発行される SQL が見えにくく、N+1 などの挙動が暗黙的になりやすい。MyBatis は SQL を自分で書くので透明性が高く、学習目的にも合う。
    • 連鎖削除の方針: 親子の削除は JPA の自動カスケードに頼らず、DB の ON DELETE CASCADE に委ねる。削除の連鎖が DB スキーマに明文化され、アプリ層に隠れたロジックを持たせずに済む。
    • トレードオフ: マッピングや SQL を自分で書くぶんボイラープレートは増える（<resultMap> の <constructor> など）。その代わり「どんな SQL が走るか」を常に把握できる。
    • 派生する判断: MyBatis はテーブル自動生成を持たないため、スキーマ管理は Flyway が必須になる（→ MyBatis Mapper の書き方）。

    認証ロードマップ

    決定: 認証は段階的に導入し、Spring Boot 側は JWT 検証のみに徹する。

    • MVP: 認証なし。初回発行 UUID でユーザーを識別する。
    • V2: Keycloak を導入し、JWT 発行・ユーザー管理を任せる。
    • V3: Keycloak に Google を IdP（外部 ID プロバイダー）として追加し、Google ログインを可能にする。
    • Spring Boot 側の方針: バックエンドは受け取った JWT の検証だけを担い、認証プロバイダーの実装には依存しない。これにより、認証基盤（Keycloak / 別サービス）を将来差し替えてもバックエンドのコードを大きく変えずに済む。認証の「発行」と「検証」の責務を分離する設計。

    状態管理に TanStack Query

    決定: モバイルのサーバー状態管理に TanStack Query を使う。

    • 対象: サーバーから取得するデータ（部屋一覧など）の管理。
    • 採用理由: キャッシュ・楽観的更新（optimistic update）・リトライ・再フェッチを標準で備えており、サーバー状態管理の定番処理を自前で書かずに済む。
    • 比較:
      • SWR: データ取得は得意だが Mutation（更新系）のサポートが弱い。
      • Zustand: 汎用の状態管理で、サーバー状態のキャッシュ・同期は自前実装になってしまう。
    • UI ローカル状態: フォーム入力やモーダルの開閉など、サーバーと無関係な UI 状態は useState で素直に扱う。「サーバー状態」と「UI 状態」を別の道具で管理し、役割を混ぜない。

    package by feature + Capability パターン

    決定: feature 単位でパッケージを切り、feature 間は直接 import せず Capability の interface 経由で依存させる。

    • 方針: 機能（feature）ごとにコードをまとめ、feature 間の直接 import を禁止する。これで 1 機能の変更が 1 ディレクトリで完結し、機能の追加・削除がしやすくなる。
    • 依存の逆転: feature 同士を直結すると循環依存・密結合に陥るため、capabilities/ に置いた interface 経由で連携させる。使う側が必要な操作を interface で宣言し、提供側がそれを実装する。
    • DI 配線: interface と実装の結びつけは di.ts の 1 か所に集約し、各 feature は相手の実装を知らずに済むようにする。
    • 関連ノート: 詳細は下記の 2 つにまとめた。

    参考: Package by Feature 構成 / Capability パターン

    Part の所属先: ポリモーフィック関連

    決定: owner_type（TEXT）と owner_id（UUID）の組み合わせで、Part が Room と Furniture の両方に属せるようにした。FK 制約は付けない。

    • 問題の背景: Part は「部屋のパーツ（例: キッチンの床）」と「家具のパーツ（例: エアコンのフィルター）」の 2 種類が存在する。それぞれ別テーブル（room / furniture）を親に持つ。
    • 選択肢と比較:
      • テーブル分割案（room_part / furniture_part テーブルを別に作る）: FK を張れて整合性が DB 層で完全に保証される。その代わり、「全パーツを取得する」クエリが UNION になり、将来パーツに共通の操作（例: 掃除記録）を書くたびに 2 テーブルを意識しなければならない。
      • ポリモーフィック関連（採用）: owner_type + owner_id で所属先を表す。パーツを 1 テーブルで扱えるためクエリがシンプルになる。代わりに FK 制約を DB 側に持てないため、整合性はアプリ層が担保しなければならない。
    • 採用理由: パーツは cleaning-record / heatmap など複数の feature が横断的に参照するエンティティになる予定。テーブルが 1 つの方が将来の JOIN や集計が書きやすい。FK なしのリスクは、application 層で削除連鎖（PartRepository.deleteByOwnerId）を明示的に呼ぶルールで対処する。
    • 二重防衛として CHECK 制約を追加: FK は張れないが、owner_type の値域は CHECK (owner_type IN ('ROOM', 'FURNITURE')) で DB 層からも守る。これにより、アプリ層のバグや直接 SQL 操作での不正値挿入を防げる。
    • トレードオフ: FK 制約がないため、owner_id の参照先が本当に存在するかどうかをアプリ層が保証しなければならない。削除処理の抜け漏れが孤立レコードを生む可能性がある。ORM（JPA）がない環境で選ぶ設計なので、削除フローのテストカバレッジを厚くすることが重要。

    CI/CD 方針

    決定: CI は GitHub Actions で自動化（lint / test）、CD は当面手動。さらにアーキテクチャ自体をテストで守る。

    • GitHub Actions: main への push / PR で lint と test を自動実行する。デプロイ（CD）は自宅サーバー運用とのかみ合わせを見ながら、当面は手動で行う。
    • アーキテクチャテスト: 「feature 間の直接 import 禁止」「レイヤーの依存方向」を口約束で終わらせず、自動テストで強制する。
      • モバイル（TypeScript）: eslint-plugin-boundaries で feature 境界を検査。
      • バックエンド（Kotlin）: Konsist でレイヤー依存方向・命名規約を検査。
    • 自動化の線引き理由: 品質に直結する CI とアーキテクチャ検査は自動化して継続的に守り、影響が大きく慎重に行いたいデプロイは手動に残す、という切り分け。
