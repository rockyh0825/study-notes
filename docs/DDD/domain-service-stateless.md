# ドメインサービスは状態を持たない

## ポイント

ドメインサービスは、**振る舞い（ロジック）を変えるために自分自身の状態を持たない**という原則で設計する。

- ドメインサービスは「誰か（どのエンティティ）の責務でもないドメインロジック」を表現する場所
- ただし、それ自体はデータを保持する主体ではない
- 呼び出しごとに渡された引数（エンティティや値オブジェクト）だけをもとに処理を行い、結果を返す

## なぜ状態を持たせないのか

ドメインサービスに内部状態を持たせてしまうと、以下のような問題が起きやすい。

- 呼び出す順番や過去の呼び出し内容によって結果が変わってしまい、挙動の予測が難しくなる
- テストのたびに内部状態を初期化する必要が生まれ、テストが複雑になる
- 複数のリクエスト・スレッドから同時に使われた場合に、状態の競合（競合状態）が起きる可能性がある

逆に状態を持たなければ、同じ入力に対して常に同じ処理結果を返す「純粋な処理」として扱えるため、これらの問題を避けられる。

## 実装イメージ（Kotlin）

```kotlin
// 良い例: 状態を持たないドメインサービス
class TransferService {
    fun transfer(from: Account, to: Account, amount: Money) {
        from.withdraw(amount)
        to.deposit(amount)
    }
}
```

この`TransferService`はフィールドに何も状態を持たず、引数として渡された`Account`や`Money`（エンティティ・値オブジェクト側）だけが状態を持つ。ドメインサービス自体はシングルトンとして使い回しても安全になる。

## エンティティとの対比

- エンティティ: 自身のライフサイクルの中で状態を持ち、時間とともに変化する
- ドメインサービス: 状態を持たず、渡されたエンティティ・値オブジェクトに対する処理（振る舞い）だけを提供する

この役割分担により、「状態を持つもの」と「状態を持たない処理」が明確に分離され、ドメインモデル全体の見通しがよくなる。
