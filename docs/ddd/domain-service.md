# ドメインサービスの切り出し方

DDDでロジックをどこに置くか迷ったとき、「エンティティ・値オブジェクト」の次に検討する置き場所がドメインサービスである。ここでは、いつドメインサービスを切るべきかの判断基準を整理する。

## ドメインサービスとは

- エンティティや値オブジェクトに自然に属さない業務ロジックを表現するオブジェクト
- 状態（フィールド）を持たない、ステートレスな存在
- ドメイン層に置かれる（インフラやアプリケーションの都合を含まない）

## いつ切り出すか

以下のいずれかに当てはまる場合に検討する。

1. **ロジックが単一のエンティティ・値オブジェクトに属さない**
   - 例: 複数の集約をまたぐ計算（口座間の送金など）
2. **外部への問い合わせが必要**
   - 例: 「メールアドレスの重複チェック」のように、リポジトリを使って他のエンティティと比較する必要がある処理
3. **「〜Service」的な動詞的処理で、どのエンティティのメソッドにするか不自然**
   - 例: `isTransferable(from, to, amount)` を `Account` のインスタンスメソッドにすると片方の口座に不自然に依存してしまう場合

## 切り出す前にまず検討すること

いきなりドメインサービスを作るのではなく、まず以下を検討する。

- そのロジックはエンティティのメソッドとして表現できないか
- そのロジックは値オブジェクトのコンストラクタ・メソッドとして表現できないか

エンティティ・値オブジェクトに自然に置けるなら、そちらを優先する。ドメインサービスは「置き場所がない」ロジックの最終手段として使う。

## アプリケーションサービスとの違い

名前が似ているため混同しやすいが役割が異なる。

| | ドメインサービス | アプリケーションサービス |
|---|---|---|
| 役割 | 業務ロジックそのもの | ユースケースの調整（トランザクション制御、リポジトリ呼び出し、ドメインサービス呼び出しの組み立て） |
| 層 | ドメイン層 | アプリケーション層 |
| 業務知識 | 持つ | 基本的に持たない（ドメイン層に委譲） |

業務ルールの判断そのものはドメインサービス（またはエンティティ・値オブジェクト）に置き、アプリケーションサービスはそれらを呼び出して1つのユースケースとして組み立てる役割に徹する。
