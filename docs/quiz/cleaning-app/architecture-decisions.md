# クイズ: 掃除アプリ アーキテクチャ決定

掃除管理アプリで下したアーキテクチャ上の意思決定と、その背景・トレードオフを確認するクイズです。

---

### Q1. データ保存方式は当初どう考え、最終的にどう決めましたか。サーバーファーストを採用した理由を3つ挙げてください。

??? success "解答"
    - 当初はローカル保存案だったが、最終的にユーザーデータを全て PostgreSQL（サーバー）に保存するサーバーファーストへ変更した
    - 理由: (1) 自宅 WiFi 前提でレイテンシが許容できる (2) 端末間同期ロジックの複雑さを回避できる (3) 機種変更にデータ移行なしで対応できる
    - トレードオフはオフライン時の挙動（ネット接続前提になる）
    - 参考: （公式ドキュメントを後で追記）

### Q2. MVP 段階では、認証なしでどうやってユーザーを識別しますか。

??? success "解答"
    - 認証は実装せず、初回起動時に発行する UUID でユーザーを識別する
    - 認証基盤の実装コストを後回しにしつつ、サーバーにユーザー単位でデータを保存できる
    - 本格的なユーザー管理は後続バージョンの認証導入で対応する
    - 参考: （公式ドキュメントを後で追記）

### Q3. BaaS（Supabase 等）も検討したうえで、なぜ Spring Boot + Kotlin の自前バックエンドを継続したのですか。

??? success "解答"
    - 学習目的・実績作り目的のため、あえて自前バックエンドを継続した
    - BaaS は早く作れるが、バックエンド設計・実装の経験という今回の目的には合わない
    - トレードオフは「自前実装の手間 vs 得られる経験」で、後者を優先した
    - 参考: （公式ドキュメントを後で追記）

### Q4. データアクセスに JPA ではなく MyBatis を選んだ理由は何ですか。連鎖削除はどう実現しますか。

??? success "解答"
    - SQL を明示的に制御したい（発行される SQL を把握・管理したい）ため MyBatis を採用
    - 連鎖削除は ORM の自動カスケードではなく、DB の `ON DELETE CASCADE` に委ねる
    - トレードオフは「ボイラープレート vs SQL の透明性」で、透明性を優先
    - 参考: （公式ドキュメントを後で追記）

### Q5. 認証のロードマップ（MVP → V2 → V3）を説明してください。各段階で何を導入しますか。

??? success "解答"
    - MVP: 認証なし（UUID 識別）
    - V2: Keycloak を導入し、JWT 発行・ユーザー管理を担わせる
    - V3: Keycloak に Google を IdP（外部 IdP）として追加し、Google ログインに対応する
    - 段階的に認証を強化していく方針
    - 参考: （公式ドキュメントを後で追記）

### Q6. 認証導入後、Spring Boot 側は認証についてどこまで責務を持ちますか。なぜその分担にするのですか。

??? success "解答"
    - Spring Boot は受け取った JWT の「検証のみ」を担い、認証プロバイダー（Keycloak 等）には非依存とする
    - 認証・ユーザー管理は Keycloak に任せ、アプリ側は検証だけにすることで関心を分離できる
    - これにより IdP の差し替え（Google 追加など）があってもバックエンドの実装が大きく変わらない
    - 参考: （公式ドキュメントを後で追記）

### Q7. モバイルのサーバー状態管理に TanStack Query を採用したのはなぜですか。SWR・Zustand と比較して説明してください。

??? success "解答"
    - キャッシュ・楽観的更新・リトライを標準で備え、サーバー状態管理に必要な機能が揃っているため
    - SWR は Mutation（更新系）が弱い、Zustand はサーバー状態を扱うと自前実装が増える、という理由で見送った
    - UI のローカル状態（サーバーと無関係な画面状態）は `useState` で扱い、サーバー状態と役割を分ける
    - 参考: （公式ドキュメントを後で追記）

### Q8. フロントエンドで package by feature + Capability パターンを採用し、どんなルールで feature 間依存を制御していますか。

??? success "解答"
    - feature 間の「直接 import」を禁止する
    - 連携が必要な場合は `capabilities/` の interface 経由で依存させ、依存の向きを逆転させる
    - interface と実装を結びつける DI 配線は `di.ts` に集約する
    - これにより feature の独立性とモジュール境界を保つ
    - 参考: （公式ドキュメントを後で追記）
