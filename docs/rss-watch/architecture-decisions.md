# RSS Watch アーキテクチャ決定ログ

RSS Watch で下したアーキテクチャ上の意思決定と、その背景・トレードオフを記録する。

---

## Kotlin(JVM)で実装する

**決定: fetcher・consumer・Web(SSE)まで全部 Kotlin で実装する。**

- **採用理由**:
    - **学習目的・実績作り**: 就活の文脈でサーバーサイド Kotlin の実装経験を積みたい。cleaning-app と同じく「自分で組むこと自体に価値がある」プロジェクト。
    - **Kafka が JVM ネイティブ**: ブローカー自体が JVM 製で、公式クライアントは Java。情報が最も厚く機能が完全なのは JVM クライアントで、Kafka Streams に至っては JVM でしか使えない。Kafka を学ぶなら JVM 言語が最短距離。
    - **自宅サーバー運用**: fat jar + systemd または Docker で安定運用できる。
- **RSS パースは Rome を使う**: JVM の定番 RSS/Atom パーサー。フィード形式の差異を吸収してくれる。
- **トレードオフ**: 軽量スクリプト言語に比べて雛形・ビルドの初期コストが大きい。1 言語で全部揃う保守性を優先する。

---

## Kafka 採用

**決定: 取得と表示の間に Kafka を挟んだイベント駆動構成にする。規模的にはオーバーキルだと理解した上で、学習題材として採用する。**

- **正直な評価**: 「1 日数回、数百件を取得して DB に書く」だけなら定期実行 + 直書きで十分。Kafka が*必要*になることはない。
- **それでも採用する理由**: RSS 収集はストリーム処理の学習題材としてほぼ理想形だから。
    - トイデータではなく**実データが継続的に流れてくる**
    - guid をキーにした冪等書き込みと組み合わせると、**at-least-once 配信 + 冪等 sink** という定番パターンをそのまま体験できる
    - fetcher / enricher / sink / notifier と**段階に分けやすい**
- **学べる核心**: consumer group とオフセット管理、key によるパーティショニング、ブローカー再起動時の再送と冪等性、「Kafka はキューではなくログである」こと。
- **トレードオフ**: 構成要素が増える(ブローカーの運用、Docker Compose、監視)。個人ツールとしての可搬性は下がる。

---

## Spring Boot 採用(vs Ktor)

**決定: フレームワークは Spring Boot にする。**

- **比較対象**: Ktor。JetBrains 製でコルーチンベース、フットプリントが小さく自宅サーバー向き。SSE も簡単。
- **採用理由**:
    - 日本のサーバーサイド求人では Spring Boot の需要が圧倒的に高く、**就活での話題性**を重視した。
    - **spring-kafka** で consumer group・バッチリスナー・エラーハンドリングの「定番の形」が学べる。
    - cleaning-app のバックエンドも Spring Boot + Kotlin なので、知識が相互に流用できる。
- **トレードオフ**: Ktor よりも重量級(起動時間・メモリ)。自宅サーバーの余裕でカバーする。

## 1 topic + 2 consumer group

**決定: topic は `rss.items` の 1 本にし、sink(DB 書き込み)と live(SSE 配信)を別の consumer group として並走させる。**

- **方針**: キーワード抽出は fetcher 側で publish 前に済ませ、topic には抽出済みのメッセージを流す(enricher を挟む多段 topic 構成は最初はやらない)。key はフィード名にしてパーティショニングの挙動を観察できるようにする。
- **2 つの consumer group の性質の違い**が学びの核:
    - **sink**: 1 件ずつ即書きせず、**まとめて書いてまとめてオフセットをコミット**(マイクロバッチ)。遅延より「確実に全件 DB に入ること」が正義。
    - **live**: 届いた瞬間に 1 件ずつ SSE でブラウザへ。低遅延が正義で、取りこぼしても致命的ではない。
- **できる実験**: sink を止めたまま fetch を回す → live はリアルタイムに流れ続けるが DB は止まる → sink を再起動すると自分のオフセットから一気に catch-up する。「consumer が落ちてもデータは失われない、それぞれが自分のペースで読める」というログとしての Kafka を体感できる。
- **トレードオフ**: enricher を分離しないため「topic → 変換 → 別 topic」(Kafka Streams の典型)は最初のスコープから外れる。学習が進んだらキーワード抽出を Kafka Streams で enricher に切り出す拡張余地を残す。

## キーワード抽出は辞書ベース

**決定: 技術キーワードの抽出は「正規化名 + エイリアス」の手書き辞書 + 正規表現で行う。ML 的な手法は使わない。**

- **仕組み**: `"Kubernetes": ["kubernetes", "k8s"]` のような辞書(約 60 分類)で、タイトル + 概要を照合する。表記ゆれはエイリアスで正規化名に寄せる。
- **採用理由**: **透明性と保守の容易さ**。なぜそのキーワードが付いたかが常に説明でき、誤検出も辞書の 1 行で直せる。追いたい技術が増えたら 1 行足すだけ。
- **日本語対応のポイント**: 正規表現の `\b`(単語境界)は日本語文中で機能しない(日本語文字も `\w` に含まれるため、`Pythonで` の `Python` 直後に境界が立たない)。そこで **前後が英数字でないことだけを lookaround で要求する独自境界** `(?<![A-Za-z0-9])...(?![A-Za-z0-9+#])` を使う。
- **誤検出しやすい短い名前の扱い**: `Go` は一般語と衝突するため、小文字無視の照合から外して **大文字小文字を区別する別枠**(`Go` 完全一致 + `golang`)で扱う。
- **トレードオフ**: 辞書にない新技術は拾えない(手動メンテが必要)。網羅性より説明可能性を取った。

## 蓄積は DB、Kafka はパイプ

**決定: データの蓄積・集計は DB(まず SQLite)が担い、Kafka は輸送路に徹する。ブラウザへのリアルタイム配信は SSE で中継する。**

- **背景**: 「fetch 結果を Kafka に publish して画面側で subscribe する」構想の解像度を上げた結果。
    - **ブラウザは Kafka を直接 subscribe できない**ので、表示側には必ず中継役(consumer 内蔵の Web サーバー)が入る。
    - 「直近 7 日の言及ランキング」のような**集計クエリは Kafka 単体では苦手**。retention で消える前提のログに検索を頼らない。
- **構成**: sink consumer が DB に書き(蓄積・集計担当)、live consumer が SSE で流す(リアルタイム担当)。画面は「DB 由来の集計」と「SSE 由来の新着」の両方を表示する。
- **SSE を選ぶ理由(vs WebSocket)**: サーバー → クライアントの単方向配信で十分なので、HTTP そのままで済む SSE が簡単。双方向が要る要件が出たら WebSocket を再検討。
- **DB の選択**: まず SQLite で始める。スキーマは `guid UNIQUE` + `INSERT OR IGNORE` の冪等書き込みを基本にし、将来 PostgreSQL(自宅サーバー)へ差し替えられるようリポジトリ層を分離しておく。

## 定期実行は @Scheduled

**決定: fetcher は Spring の `@Scheduled` で常駐プロセス内から定期巡回する。**

- **採用理由**: 外部スケジューラ(cron / launchd)への依存が消え、デプロイ物が 1 つにまとまる。巡回間隔の変更もアプリ設定で完結する。
- **トレードオフ**: 常駐化するとプロセスが落ちたときに巡回も止まる。systemd の自動再起動で対処する。
