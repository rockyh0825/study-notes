    クイズ: Capability パターン

    feature 間の直接依存を避ける Capability パターン（依存の逆転）の目的・仕組み・DI 配線を確認するクイズです。

    Q1. Capability パターンが解決しようとしている課題は何ですか。

    解答
    • feature 同士が直接 import すると、モジュール境界が崩れ、双方向依存・循環依存が生まれる
    • Package by Feature の「機能ごとに独立」という前提が壊れることを防ぎたい
    • feature を疎結合に保ち、互いの実装を知らずに連携できるようにするのが目的
    • 参考: Package by Feature 構成

    Q2. 「使う側視点で interface を定義する」とはどういう意味ですか。なぜ提供側ではなく使う側が定義するのですか。

    解答
    • 機能を「使う側」が必要とする操作だけを interface（capability）として宣言する
    • 使う側が必要な分だけを定義するので、提供側の都合に引きずられず、必要最小限の契約になる
    • これにより依存の向きが「使う側 → 抽象（interface） ← 提供側の実装」となり、具体実装への直接依存を避けられる
    • 参考: （公式ドキュメントを後で追記）

    Q3. このパターンで「依存の逆転」が起きるとは、具体的に依存の向きがどう変わることですか。

    解答
    • 通常は「使う側 feature → 提供側 feature の実装」へ直接依存してしまう
    • Capability パターンでは両者が capabilities/ に置かれた interface（抽象）に依存する
    • 提供側 feature が interface を実装する側に回るため、依存の向きが具体から抽象へ逆転する（依存性逆転の原則 DIP）
    • 参考: （公式ドキュメントを後で追記）

    Q4. interface と実装を結びつける DI 配線を di.ts の1か所に集約する利点は何ですか。

    解答
    • どの interface にどの実装が紐づくか（配線）が1か所に集まり、依存関係を俯瞰しやすい
    • 各 feature は相手の「実装」を直接 import せず、interface だけを知れば済む
    • 配線を差し替えるだけで実装を切り替えられる（環境別・モック差し替えが容易）
    • 参考: （公式ドキュメントを後で追記）

    Q5. テスト時、Capability パターンはどんな利点をもたらしますか。

    解答
    • 使う側は interface に依存しているため、テストでは interface を満たすモック/スタブを差し込める
    • 提供側 feature の実装（DB アクセス等）を呼ばずに、使う側の振る舞いを単体テストできる
    • DI 配線をテスト用に差し替えるだけでよく、対象コードを書き換えずに済む
    • 参考: （公式ドキュメントを後で追記）

    Q6. Capability パターンの注意点・過剰設計のリスクは何ですか。採用の判断基準は。

    解答
    • interface が増えすぎて間接化が進み、コードが追いにくくなる懸念がある
    • 連携が少ない・feature 間依存がほぼ無い小規模では過剰設計になりうる
    • 「feature 間の連携が実際に発生し、直接 import を避けたい」場面に限定して適用するのが判断基準
    • 参考: （公式ドキュメントを後で追記）

    Q7. Capability パターンと Package by Feature は、どういう関係にありますか。

    解答
    • Package by Feature は「機能単位で分ける」構成の方針
    • その構成で必ず生じる「feature 間の依存をどう扱うか」という課題に対する解決策が Capability パターン
    • 両者はセットで使われることが多く、Capability パターンは Package by Feature の境界を守るための仕組みと言える
    • 参考: Package by Feature 構成
